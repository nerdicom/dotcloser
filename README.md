# DotCloser

**Turn domains into deals.** A domain seller workspace with a custom logo and favicon, portfolio import, buyer research, contact review, editable email offers, subscription billing, and sending through the seller's own mailbox.

## What is implemented

- Google and Facebook sign-in, with explicit linking of additional sign-in methods. Accounts are never merged just because two providers return the same email.
- Seven-day application-managed trial from signup, ten total outbound emails, no payment card required. Standard allows fifty outbound emails per UTC day. Stripe Checkout upgrades immediately without granting a second trial.
- Portfolio management with per-domain USD asking prices, individual entry, and CSV bulk import. Up to 5,000 domains per user.
- RegCount and licensed dotDB related-domain adapters, public source attribution, manual buyer entry, optional Hunter published role-contact lookup, and explicit contact review.
- Editable message templates incorporating the selected domain, asking price, seller identity, and buyer relevance. Messages are not automatically generated by an LLM or sent when researching.
- Separate Gmail/Google Workspace and Outlook/Microsoft 365 sending authorization. Encrypted refresh tokens, server sessions, CSRF protection, OAuth state binding, and PKCE where supported.
- Final review with recipient list and saved message previews; an atomic queue reservation enforces limits before sending. Individual messages, not visible bulk CC lists.
- Send-status activity, safe cancellation of queued messages, unsubscribe links, suppression, no automatic retries after uncertain provider outcomes, and messages saved by the sending provider.
- Mobile layouts with consistent field grids, native accessible dialogs, and keyboard focus indicators.
- Explicit interactive preview with example businesses and no real email sending.

## Start locally

Use **Node.js 24**. The server uses the built-in `node:sqlite` driver.

```sh
npm ci
cp .env.example .env
npm run build
npm test
npm start
```

For local development use `NODE_ENV=development` and `APP_URL=http://localhost:3000`. Production deliberately refuses to start without HTTPS `APP_URL`, `ENCRYPTION_KEY`, and `SESSION_SECRET`.

Generate two separate secrets; never put their values in GitHub:

```sh
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

Set the first output as `ENCRYPTION_KEY`, and a second output as `SESSION_SECRET`. Keep the encryption key stable or existing mailbox tokens will become unreadable. Keep the session secret stable so previously sent unsubscribe links continue working.

The public preview needs no OAuth or billing credentials. It is not an authenticated account and cannot send. All real data and actions require sign-in.

## Hostinger deployment

This is a **Node application**, not a static `public_html` website. Uploading only `public/` will not provide login, billing, persistence, or email sending.

### Recommended for this build: Hostinger VPS

Use a VPS with Docker and a durable named volume. The supplied configuration runs a single app/worker process and binds it only to localhost port 3090. It does not replace existing websites or services.

```sh
git clone https://github.com/nerdicom/dotcloser.git
cd dotcloser
cp .env.example .env
# Edit .env with production values and account credentials.
docker compose up -d --build
```

Add the site block from `deploy/Caddyfile.example` to an existing Caddy server, or configure the existing Nginx/Apache reverse proxy for `127.0.0.1:3090`. Do not replace a server configuration that hosts other projects. Open only the public reverse proxy ports; keep the application port private.

Point Cloudflare's apex A record to the VPS, add `www`, and use **Full (strict)** TLS with a valid origin certificate. Disable caching for `/api/*`, `/auth/*`, and `/unsubscribe/*`; never cache authenticated responses. The server emits `Cache-Control: no-store` for API responses.

For updates, run `git pull --ff-only` and `docker compose up -d --build`. The `dotcloser_data` named volume retains the SQLite database. Back it up using SQLite's online backup or a stopped-container snapshot; copying an active SQLite file alone can miss WAL data. Keep copies off the VPS. Do not run multiple app replicas against this SQLite database: use one worker and migrate storage/queueing before scaling horizontally.

### Hostinger managed Node hosting

Hostinger offers Node hosting on supported Business/Cloud plans. Use **Node 24**, install `npm ci`, build `npm run build`, and start `npm start`, with the application's assigned `PORT`. **This version needs a guaranteed persistent database path outside replaced deployments.** If the plan does not provide one, deploy the supplied VPS configuration or migrate the persistence layer to Hostinger MySQL/external managed storage first. A redeployed ephemeral SQLite path is not production-safe. Do not upload this as a frontend-only project.

## Accounts to configure before live launch

### 1. Google login and Gmail

Create a Google Cloud OAuth web application, enable Gmail API, configure the consent screen and authorized domain `dotcloser.com`.

- Redirect URI: `https://dotcloser.com/auth/google/callback`
- Login scopes: `openid email profile`
- Mail connection additionally requests `https://www.googleapis.com/auth/gmail.send`, offline access, and explicit consent.
- Set `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` on the server.
- Complete Google's verification/review required for the app's audience and sensitive Gmail sending scope. In testing mode, only configured test users can authorize and refresh-token lifetimes can be limited.
- Google API policies: `https://developers.google.com/terms/api-services-user-data-policy`

The sign-in permission and mailbox connection are separate. Mail access is not requested during initial sign-in. Users can disconnect in Settings and revoke the app from their provider account.

### 2. Facebook sign-in

Create a Meta app with Facebook Login for web. Configure the app domain, website URL, privacy and data deletion URLs, and required app review/business verification for a public audience.

- Redirect URI: `https://dotcloser.com/auth/facebook/callback`
- Privacy URL: `https://dotcloser.com/privacy.html`
- Terms URL: `https://dotcloser.com/terms.html`
- Data deletion instructions: `https://dotcloser.com/data-deletion.html`
- Set `FACEBOOK_CLIENT_ID`, `FACEBOOK_CLIENT_SECRET`, and the supported `FACEBOOK_API_VERSION` (default `v25.0`).
- Uses `public_profile,email`. Users must share an email to create an account. Facebook is a sign-in method, not an email sending provider.

### 3. Outlook / Microsoft 365 mailbox sending

Create a Microsoft Entra application with delegated Graph permissions. If personal and work/school mailboxes are wanted, choose the app registration audience that includes both.

- Redirect URI: `https://dotcloser.com/auth/microsoft/callback`
- Delegated scopes: `openid profile email offline_access User.Read Mail.Send`
- Set `MICROSOFT_CLIENT_ID`, `MICROSOFT_CLIENT_SECRET`, and `MICROSOFT_TENANT=common`.
- Tenant admins may restrict consent. Complete any required publisher verification or admin consent.

Only Gmail and Microsoft mailbox sending are implemented. Hostinger Mail, SMTP, IMAP, other mailbox providers, inbox reading, automated replies, and follow-up sequences are not included in this release.

### 4. Stripe subscription

Choose the Standard monthly price in Stripe and create one recurring **monthly** Price. No price has been invented in the application; the UI reads the actual configured Stripe price.

- Set `STRIPE_SECRET_KEY`, `STRIPE_PRICE_ID`, and `STRIPE_WEBHOOK_SECRET`.
- Webhook endpoint: `https://dotcloser.com/api/billing/webhook`
- Subscribe to `checkout.session.completed`, `customer.subscription.created`, `customer.subscription.updated`, `customer.subscription.deleted`, `invoice.paid`, and `invoice.payment_failed`.
- Enable the Stripe customer billing portal for payment updates/cancellation.
- Verify with Stripe test mode before using live keys.
- Seven trial days and ten trial sends are controlled by the application from signup. Checkout is for paid Standard, so it does not restart a trial. Standard is granted only from signed webhook reconciliation, never from a browser redirect.
- Open Checkout sessions are reused to reduce duplicate purchases. Subscription events reconcile current eligible subscriptions to tolerate duplicate/out-of-order delivery.

### 5. Buyer research and contacts

These integrations are disabled by default until access and reuse rights are confirmed.

- **RegCount:** `REGCOUNT_ENABLED=true`, with `REGCOUNT_API_URL=https://regcount.com`. Adapter uses the application's `GET /api/search?q=keyword&position=any` response, validated against the RegCount source available for this project. It requires live non-demo results and a source timestamp. Only the first result page is imported, up to fifty candidates. Coverage depends on the RegCount index and is not claimed to equal all registered domains.
- **dotDB:** set `DOTDB_ENABLED=true` and `DOTDB_API_KEY`. Uses documented `https://api.dotdb.com/v2/search?keyword=...&page=1` with `Authorization: Token`. Confirm that your API agreement permits this multi-user product and display/use of results; an API subscription alone is not treated as blanket redistribution permission. This app does not scrape dotDB.
- **Contacts:** optional `HUNTER_API_KEY` enables documented `GET https://api.hunter.io/v2/domain-search`. Only generic business addresses with a published source are shown. No addresses are guessed from name patterns. Enable only with an appropriate provider plan and permitted use. Sellers select/review contacts before drafts can be sent.
- Without these providers, authenticated users can still add relevant businesses and published contacts manually.

### 6. Public launch details

Create working `support@dotcloser.com` and `privacy@dotcloser.com` mailboxes/aliases. The included policy pages are baseline launch text for owner review, not a claim of legal review. Confirm the operator details, retention handling, and actual support process before launch. The user-facing product identifies Nerdi, LLC as operator.

## Limits and sending behavior

- Trial: seven elapsed 24-hour periods after signup, with ten total reserved/accepted/uncertain sends. The trial ends when time expires or allowance is used. Reconnecting mail or changing sign-in providers does not reset it.
- Standard: fifty sends per UTC day. Queued/sending messages reserve allowance; provider-accepted and unknown outcomes count on their attempt day. A queued batch cannot exceed available allowance.
- A user must save their sender name and postal business address, connect a sending account, review buyer contact/source, save drafts, and explicitly confirm the campaign.
- The single worker submits one message every sixty seconds by default. Message submission is serial and uses the user's mailbox. This is a deliberately conservative initial sending rate.
- A successful Gmail response or Microsoft `202` means the provider accepted the message, not guaranteed delivery. Replies/bounces stay in the user's mailbox; the app does not pretend to track them.
- A timeout is marked `unknown` and never retried automatically. Check the provider's Sent folder. Accepted/sending/unknown domain-recipient pairs cannot be duplicated.
- Cancelled unsent or definitely rejected sends can be selected again and retried through a new explicit campaign confirmation.
- Unsubscribing suppresses that recipient for the seller and cancels their queued emails. Suppression is checked at reservation and immediately before sending.

## Verification

`npm test` checks trial and daily limits, atomic batch failure, tenant isolation, duplicate prevention, safe retries, uncertain outcomes, CSRF, encryption, and unsubscribe cancellation without sending real emails. `npm run build` validates JavaScript and required assets. DOM interaction checks also passed for initialization, domain entry, draft selection, exact-message review, the unsaved-draft guard, settings labels, and billing. Provider calls require end-to-end test accounts after their credentials are configured. Browser visual QA was unavailable in the build environment; responsive grid alignment is implemented but should be checked in the deployed app before opening paid signups.

## Architecture

`public/` contains the responsive browser workspace and generated logo; `server/` contains Express, SQLite persistence, OAuth, Stripe, source adapters, and the conservative queue worker. Runtime data and secrets are excluded from Git. The app has no dependency on ChatGPT or a shared owner mailbox to send users' campaigns.
